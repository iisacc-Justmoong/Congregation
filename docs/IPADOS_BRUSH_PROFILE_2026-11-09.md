# iPad 브러시와 색상 입력 성능 기록

## 범위와 방법

2026-11-09에 USB로 연결된 iPad Pro 12.9형 4세대, iPadOS 27.2에서
사용자가 브러시, 색상 피커, 도구 전환을 각각 조작했다. Instruments Time
Profiler는 전체 프로세스의 실행 중 스레드를 표본화했고, 별도 표는 250ms 이상
주 스레드 멈춤 후보를 기록했다. 표본은 호출 스택을 포함하는 포괄 수치이므로
하위 경로와 상위 경로의 비율을 더할 수 없다. 대기 시간, 실제 화면 표시 시각,
GPU 실행 시간이나 펜 끝에서 화면 빛까지의 지연을 측정한 값은 아니다.

사용자가 각 조작을 순서대로 수행하고 완료를 알렸지만 브러시 크기, 간격,
확대율, 레이어 수의 기계 판독 기록이나 고속 카메라 영상은 수집하지 못했다.
따라서 서로 다른 기록의 숫자를 동일 부하의 엄밀한 전후 비교로 취급하지 않는다.
로컬 증거는 `build/ipados/performance-20261109/`의 `.trace`와 내보낸 XML이다.

## 기존 설치본

기존 1.0.2 (3) 실행 파일 UUID는 `032A96B5-37DA-39DB-B0E7-9E7F97E82957`이다.
브러시 전용 기록은 66.26초이며, 38–54초의 주 스레드 실행 표본 15,707개 중
`BitmapEditJournal::preview`를 포함한 표본은 11,479개(73.1%), 그 안에서
기존 `apply` 경로를 포함한 표본은 10,661개(67.9%)였다. 기록의 멈춤 후보 중
가장 긴 항목은 5.36초였다. 사용자는 필압을 이용한 긴 획에서 지연이 크다고
보고했다. 이 결과는 CPU 표본의 연관성을 보이며 GPU 병목을 측정하지 않는다.

색상 전용 기록의 15–29초 주 스레드 표본 13,968개 중 `State::paint_tools`를
포함한 표본은 7,560개(54.1%), `WidgetMount::snapshot`을 포함한 표본은
6,430개(46.0%)였다. 두 경로는 겹친다. 가장 긴 멈춤 후보는 1.76초였고,
사용자는 색상 변경에 초 단위 지연이 있다고 보고했다. 도구 전환 전용 기록에는
최대 0.70초의 멈춤 후보가 있었고 사용자는 약 1초의 반응 지연을 보고했다.

## 증분 획 처리 빌드

2026-11-08에 빌드한 증분 획 처리 앱을 데이터 컨테이너를 유지하며 설치했다.
기록에서 확인한 실행 파일 UUID는 `FB2DCBA9-EE97-31C7-8F1F-72D5F4F3E5DD`이다.
사용자는 긴 획의 지연이 체감될 만큼 줄었다고 답했다. 색상 피커는 약 초당
한 번씩 움직이는 수준이고 도구 전환은 개선됐으나 즉시 반응하지 않는다고
보고했다.

이 기록의 브러시 조작으로 추정되는 21–39초 주 스레드 표본 12,771개 중
iiGUI `rasterize_foreground_region`을 포함한 표본은 5,513개(43.2%),
`renderFrameRegion`을 포함한 표본은 2,505개(19.6%)였다. 색상 조작 구간으로
추정되는 67–78초 표본 9,633개 중 `paint_tools`는 4,451개(46.2%),
`WidgetMount::snapshot`은 4,370개(45.4%)에 포함됐다. 주소는 동일 UUID의
빌드 바이너리로 심볼화했다. 표본은 겹치며 표시 완료나 GPU 비용을 뜻하지
않는다. 이 기록은 세 조작을 한 파일에서 순차 수집했다.

## 적용한 변경과 한계

색상 변경 시 캔버스 색과 그라디언트 기본색을 갱신하되, 색상과 무관한 필압
곡선은 다시 그리지 않는다. 현재 뷰에 없는 `brush-preview`의 반복 검색도
제거했다. 실제 피커와 필압 곡선의 상태는 관련 테스트에서 확인한다. 수정 후
색상 변경 수정본 UUID `3AB58615-4A5C-3995-B8E7-17C010361066`을 iPad에
설치해 실행했고, 캡처된 화면은 정상 표시 상태였다. 그러나 후속 Instruments
연결은 기기를 오프라인으로 표시해 사용자의 색상 조작이 포함된 비교 기록을
얻지 못했다. 정지 화면만으로는 색상 조작의 지연이나 암전 재발 여부를
확인할 수 없다. 이 기록 이후 구현한 래스터 타일 이력은 위 설치본에 포함되지
않는다. 이를 포함하는 arm64 iPadOS 빌드 UUID는
`BE9E15ED-B260-3487-8B36-6AF3EA37DC7A`이며, 빌드와 관련 자동 검사는
완료됐지만 이 빌드의 기기 설치와 펜 입력 측정은 수행하지 않았다.

타일 이력은 래스터 픽셀과 함께 획 전후의 저작 정보 및 문서 형식 버전을
보관한다. 문서 전체 바이트가 Undo/Redo에서 정확히 복원되는지, 예산 초과와
저장 잠금에 실패했을 때 기존 상태와 Redo가 보존되는지 회귀 검사한다.

헤드리스 `Congregation.stroke_performance`는 직렬화, 누름, 한 이동 입력,
512×512 영역의 CPU 합성, 놓기를 별도 계측한다. 요청된 `new` 바이트 수는
최대 메모리가 아니며 파일 동기화와 호스트 부하가 벽시계 시간에 영향을 준다.
기본 검사는 512와 2K, 작은 붓과 큰 붓을 다루고 `--extended`는 4K와 8K를
추가한다. iPad 입력이나 화면 전체의 결과로 치환하지 않는다.

같은 호스트에서 빈 단일 래스터 문서와 32px 붓을 사용한 확장 검사는 4K에서
획 시작 33ms·전체 직렬화 38ms, 8K에서 획 시작 134ms·전체 직렬화 153ms를
기록했다. 획 종료 구간의 일반 C++ 할당 요청 합은 각각 약 68MB와 270MB였다.
각 값은 한 번의 실행이며 디스크 동기화와 당시 부하가 포함된다. 파일 크기나
최대 메모리가 아니고 iPad에서의 시간도 아니다. 그럼에도 동일 붓에 문서의
전체 픽셀 수를 따라 시작과 종료 비용이 커지는 경로를 확인하는 근거가 된다.
일반 래스터의 변경 타일 이력 적용 후 같은 호스트 검사에서는 4K와 8K 획
시작이 각각 0.129ms와 0.143ms로 기록됐다. 8K 획 종료의 일반 C++ 할당 요청
합은 여전히 약 270MB였으므로 저장 시 문서 복사 문제는 남는다. 256×256 CPU
합성은 512×512 결과의 같은 부분과 픽셀별로 일치했고, 해당 한 번의 8K 호스트
실행에서는 각각 1.28ms와 5.66ms였다. 이 결과만으로 표시 타일 크기를 바꾸면
늘어나는 레이어·타일 수까지 이득이라는 결론은 내릴 수 없다.

측정 중 macOS 개발 셸의 `DYLD_*` 경로가 CMake에서 선택한 iiPaintEngine보다
오래된 `~/.local` 설치본을 먼저 로드하는 것이 확인됐다. 해당 잘못된 조합의
초기 큰 붓 결과는 기각했다. 현재 관련 CTest는 이 환경 변수를 제거하고 링크된
패키지를 사용한다. iPad의 정적 링크 결과와 이 macOS 로더 문제는 별도이다.

동일 iPad의 Photoshop 앱은 설치되어 있지 않아 동조건 비교를 하지 못했다.
프레임 분포, 실제 GPU 제출·표시 시각, 4K·8K 및 다중 레이어의 iPad 부하,
텍스처 브러시, 고속 카메라 지연은 추가 측정 대상이다. 이번 표본만으로 GPU
브러시 전면 재작성이나 특정 플랫폼 전체의 성능을 결론 내리지 않는다.

## 다중 타일 합성 개선 계약

같은 프레임의 표시 대상 중 캐시에 없는 타일은 기존 iiSharedCanvas 다중 타일
합성으로 묶는다. 각 타일의 위치·크기·샘플링과 선택 미리보기는 개별 합성의
결과와 같아야 하며, 변경되지 않은 타일은 재생성하지 않는다. 레이어별 임시
타일이 과도하게 늘지 않도록 한 번에 합성할 타일 수를 제한한다. 빈 캐시,
타일 경계의 획, 선택 미리보기, 필터와 확대 상태에서 결과 및 호출 수를
회귀 검사한다. 호출 수와 소요 시간은 CPU 합성의 관측치이며 화면 표시 완료
또는 iPad의 체감 지연으로 해석하지 않는다.
비활성화되었거나 불투명도가 0인 필터는 합성 결과에 영향을 주지 않으므로
획 손상 영역 밖의 캐시를 무효화하지 않는다. 활성 필터가 있는 경우에는 이전과
같이 영향 범위를 보수적으로 전체 표시 영역으로 잡는다.

`CanvasView`는 캐시에 없는 타일만 요청 순서대로 최대 네 개씩 묶고, 문서의
레이어 수가 많으면 묶음을 더 작게 한다. 임시 레이어 타일을 가능한 한
16개 이하로 제한하며, 단일 타일조차 이 한도를 넘는 레이어 수에서는 한 개씩
처리한다. 이 값은 임시 합성 타일 수에 관한 정책이지 전체 메모리 사용량의
상한은 아니다. 타일별 표시 캐시와 선택 오버레이, 부분 손상 영역을 유지한다.
`Viewport::composition_batches`는 CPU 합성 API가 성공한 호출 수를 관측한다.

동일 Mac에서 `TileCompositionPerformance`로 1024×1024, 래스터 두 레이어,
512×512 출력 네 타일의 개별 호출과 묶음 호출을 각각 다섯 번 번갈아 비교했다.
픽셀은 매번 일치했다. 중앙값은 필터가 없을 때 91.532ms와 91.152ms였고,
한 레이어에 반전 필터가 있을 때는 209.522ms와 143.572ms였다. 후자는 해당
시험에서 약 31.5% 감소했으며, 필터 없는 차이는 사실상 이 측정의 변동 범위로
취급한다. 이는 SDK CPU 합성만을 측정한 합성 부하로, 이미지 변환·위젯 갱신·GPU
제출·화면 표시와 iPad 입력 지연을 포함하지 않는다. 한 타일만 변경된 획에는
여러 타일의 공통 준비를 공유하는 효과가 없다.

네이티브 테스트를 구성한 `build/`에서 다음 명령으로 같은 픽셀 일치 검사와
비교 계측을 재실행한다. 시간은 통과 기준이 아니며 측정 환경에 따라 달라진다.

```sh
cmake --build build --target tests_tile_composition_performance
ctest --test-dir build -R '^Congregation.tile_composition_performance$' -V
```

다중 타일 합성을 포함한 iPadOS arm64 앱은 `build/Congregation.app`으로
빌드했다. 실행 파일 UUID는 `0F3FDF4F-EB71-323A-84C4-4AAB24030B07`이다.
이번 빌드의 기기 설치와 실제 사용 측정은 수행하지 않았다.

일반 래스터 획 확정과 Undo/Redo의 `DocumentFile::edit` 전체 문서 복사 및 동기
커밋은 이번 변경에 포함되지 않는다. 변경된 타일과 정확한 저작 정보·버전을
원자적으로 함께 반영하는 경로가 필요하며, 실패 시 문서·파일·이력의 일치를
보장한 후 별도로 적용해야 한다. 색상 피커·도구 전환과 iPad의 실제 표시 지연도
이번 시험만으로 해결됐다고 판단하지 않는다.

## 후속 변경: 획 확정과 이력의 타일 저장

위 미완료 항목을 후속 변경에서 다뤘다. 단일 자산의 일반 래스터 획은 선택과
테이퍼를 포함해 변경 타일 및 저작 정보·형식 버전을 하나의 파일 트랜잭션으로
확정하고, Undo/Redo 스택에서도 같은 정보를 복원한다. 구조 변경이 없는 일반
유한 청크 획에도 이 경로를 적용하며 선택과 테이퍼도 손상 타일로 처리한다.
공유 프레임 복사, 변형된 일부 청크 획과 구조 변경은 기존 전체 문서 경로가 남아 있다.

동일 Mac의 4K 빈 캔버스와 32px 붓, 작은 획 한 번에서 확정·Undo·Redo의 일반
C++ 할당 요청 합은 변경 전 각각 68,367,149·67,144,753·67,241,549바이트,
변경 후 1,471,942·350,150·346,334바이트였다. 별도의 4K 선택 획과
선택·테이퍼 획의 확정은 각각 1,187,534바이트와 1,833,621바이트였다.
청크 시험에서는 이력 예산이 넉넉한 문서의 작은 획 확정이 25,585,685바이트에서
316,202바이트로 줄었다. 같은 문서의 선택 획 확정은 51,315,718바이트에서
720,429바이트로 줄었고 선택·테이퍼 획 확정은 655,464바이트였다.
이 수치는 각 한 번의 일반 `new` 요청 합이며 최대
상주 메모리나 iPad 측정치가 아니다.

파일 잠금과 할당 실패를 주입한 시험은 실패 시 문서·파일·이력 스택의 기존
상태를 확인한다. 이 변경도 내구성 있는 SQLite 커밋이 끝날 때까지 동기적으로
기다린다. 외장 저장소에서 측정된 동기화 지연은 남아 있으며, 이 수치로 iPad의
펜 지연이나 사용자 체감이 개선됐다고 단정하지 않는다.
