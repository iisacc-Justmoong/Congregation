# 드로잉 성능 조사와 리팩터링 후보

## 범위와 증거 상태

2026-11-10에 현재 작업 트리의 입력·브러시·타일 합성·표시·저장 경로를
조사했다. 연결된 iPad Pro 12.9형 4세대에서는 Congregation 1.0.2 (3)이
실행 중인 것을 CoreDevice로 확인했다. Instruments는 연결이 자주 끊겨
1.388초만 기록했고, 그 구간에는 브러시 조작이 없다. 이 짧은 기록에서
설치된 실행 파일의 UUID는 `60176F6E-124E-37F2-BF46-A2F64D22B79D`로
확인됐고, 로컬 iPad 빌드의 UUID `C432059D-18BD-3C94-8224-9F9694F68BD5`와
다르다. 두 바이너리의 구체적인 차이는 확인하지 못했다. 따라서 이번 조사에는
현재 iPad의 펜 입력, GPU 또는 화면 표시 완료 표본이 없으며 현재 소스와
설치본이 같다고 단정하지 않는다. 앱을 교체하거나 현재 문서를 닫지는 않았다.

기존 iPad 기록은 [11월 9일 조사](IPADOS_BRUSH_PROFILE_2026-11-09.md)에
있다. 당시 증분 획 빌드의 브러시 조작 추정 구간에서는 주 스레드 실행 표본에
`rasterize_foreground_region`이 43.2%, `renderFrameRegion`이 19.6% 포함됐다.
이 값은 포괄 표본이라 서로 겹치며, 당시 빌드에 대한 결과이지 현재 실행본의
CPU 점유율이나 GPU·입력 지연을 뜻하지 않는다.

이번에는 Apple M1 Max의 macOS에서 기존 Release 구성 헤드리스 시험을
실행했다. 데이터베이스 임시 파일은 USB로 연결된 `Storage` 볼륨의
`Product/Congregation/resources/`에 생성됐다. 벽시계 시간은 저장 장치,
파일 시스템 및 당시 시스템 부하의 영향을 받는다. 원본은 다음과 같다.

- [512·2K 브러시 시험 로그](../build/performance-20261110/stroke-benchmark-repeat.log)
- [4K 획 시험의 프로세스 표본](../build/performance-20261110/stroke-history-4k.sample.txt)
- [긴 획 정확성 시험의 표본](../build/performance-20261110/long-stroke.sample.txt)
- [연결 직후 종료된 iPad 기록의 목록](../build/performance-20261110/ipad-brush-toc.xml)
- [해당 기록의 짧은 CPU 표본](../build/performance-20261110/ipad-short-samples.xml)

마지막 표본은 측정 구간이 주로 프로세스와 라이브러리 초기화에 걸려 있어
드로잉 비용을 판별하는 근거로 사용하지 않는다. 1,200개 이동 입력의 긴 획
시험 자체는 통과했으며 표시·확정·저장 실패 후 복구를 검증한다. 이는 지연
분위수나 실제 UIKit·Metal 화면을 측정한 결과는 아니다.

## 새로 관측한 결과

한 번씩 실행한 512×512와 2048×2048 단일 레이어 시험에서 8px·128px 붓의
획 확정은 0.923–1.163초, Undo는 0.769–1.602초, Redo는 0.842–1.418초였다.
이 결과는 위 USB 저장소에서의 Mac 시험이며 iPad의 수치가 아니다. 별도의
4K 시험 표본에서는 `Artwork::end_input`에서 타일 이력 게시와 SQLite
`COMMIT`, `unixSync`, `fcntl`로 이어지는 호출이 주 스레드에 포착됐다.
변경 타일만 저장하더라도 내구성 커밋의 완료를 동기적으로 기다리는 경로가
남아 있음을 보여 준다. 저장의 원자성과 실패 복구를 제거하라는 의미는 아니다.

같은 반복 시험에서 첫 사례를 제외한 512×512 CPU 타일 합성은 약
4.8–5.1ms, 256×256 합성은 약 1.2–1.3ms였다. 측정 구간의 일반 C++
할당 요청 합은 각각 약 6.0MiB와 1.5MiB였다. 512×512 첫 사례는 약
146ms로 변동이 컸다. 이는 각각 한 번의 호출과 요청 합이지 최대 상주
메모리나 iPad 프레임 시간은 아니다. 색상 변환, 텍스처 업로드, GPU 실행과
실제 화면 표시는 포함하지 않는다. 작은 타일을 무조건 선택하면 늘어나는
타일 수와 호출 비용이 별도로 있으므로 해당 결과만으로 크기를 결정하지 않는다.

## 우선 리팩터링 후보

1. **획 확정과 이력의 저장 대기 분리.** `CanvasView::input`의 포인터 종료가
   `Artwork::end_input` 및 동기 트랜잭션을 기다린다. 변경 타일·저작 정보·형식
   버전을 순서가 있는 내구성 작업으로 넘기고 화면과 입력을 계속 처리하도록
   검토한다. 작업 실패, 앱 종료, 연속 획, Undo/Redo가 교차하는 경우의 메모리·
   파일·이력 일관성과 실패 알림을 설계하고 검증해야 한다. 단순히 디스크
   동기화를 끄거나 성공 전에 내구성을 약속해서는 안 된다.
   [입력 종료](../App/Native/CanvasView.cpp), [획 확정](../App/Native/Artwork.cpp),
   [타일 게시](../../../SDK/iiSharedCanvas/src/Bitmap/BitmapEditJournal_p.cpp).

2. **입력 수집과 브러시 계산의 결합 완화.** UIKit은 coalesced 표본을 순서대로
   보내지만, 각 이동 이벤트에서 `Artwork::extend_input`을 호출하고 브러시
   픽셀을 처리한 다음 돌아온다. 무거운 표본이 주 스레드에 쌓일 가능성이 있다.
   입력의 시간·좌표·필압·기울기를 빠짐없이 보존하는 순서 있는 큐와 단일
   문서 소유 작업자를 검토한다. 과거 화면 갱신은 합쳐도 실제 입력 표본은
   버리지 않아야 하며, 선택·혼합 순서와 브러시 결과의 동등성을 검사한다.
   [UIKit 입력](../../../SDK/iiGUI/src/Widgets/NativeWidgetsIOS.mm),
   [획 이동](../App/Native/CanvasView.cpp).

3. **브러시 표본과 64×64 타일의 반복 복사 절감.** 현재 일반 획의 증분
   경로도 자국을 픽셀 표본 벡터로 투영한 뒤 타일별 벡터와 맵으로 분류하고,
   만진 타일의 복사본을 만들며, 이전 미리보기와 비교해 변경을 게시한다.
   자주 쓰는 브러시의 스트리밍·재사용 버퍼와 타일에 직접 기록하는 경로를
   검토한다. 실패 시 원자적 게시, 기존 픽셀 충돌 검증, 블렌드와 필압 정확성은
   유지해야 한다. [픽셀 투영](../../../SDK/iiSharedCanvas/src/Bitmap/BitmapEditor.cpp),
   [타일 준비](../../../SDK/iiSharedCanvas/src/Bitmap/StrokeComposite_p.hpp),
   [타일 미리보기](../../../SDK/iiSharedCanvas/src/Bitmap/BitmapEditJournal_p.cpp).

4. **표시 타일의 합성·변환·업로드 경로 정리.** 손상된 표시 타일을 다시
   합성한 뒤 ARGB를 RGBA 벡터로 변환해 새 이미지를 만들고, Metal의 이미지
   캐시는 새 이미지에 새 텍스처를 만들고 픽셀을 업로드한다. 타일별 지속
   텍스처와 변경 영역 업로드, 픽셀 포맷 및 버퍼 소유권 공유를 계측해 검토한다.
   장면은 부분적으로 다시 그릴 수 있지만 최종 drawable에는 현재 창 전체를
   블리트한다. 이 비용 역시 별도로 측정하며, drawable 교체 시 이전 픽셀이
   보존되는 조건을 증명하기 전에는 단순 부분 복사로 바꾸지 않는다.
   [타일 합성 및 변환](../App/Native/CanvasView.cpp),
   [Metal 이미지와 표시](../../../SDK/iiGUI/src/Graphics/CanvasMetal.mm).

5. **런타임 예산과 프레임 관측 강화.** iPad 호스트는 디스플레이 콜백에서
   이벤트 루프, 프레임 단계, 위젯 표시를 처리한다. 기본 이벤트 처리 예산은
   4ms이지만 일반 콜백을 중간에 선점하지 않으므로 콜백 하나가 길면 예산을
   초과할 수 있다. 수신·대기·붓 계산·타일 반영·CPU 합성·업로드·GPU 완료·
   표시를 별도로 계측하고, 긴 작업을 안전하게 나누거나 작업자에게 옮긴다.
   현 호스트가 요청하는 프레임 속도 범위의 선호값은 60이므로 실제 디스플레이
   콜백과 프레임 간격도 함께 기록한다. 이는 기기가 반드시 60Hz로 제한된다는
   뜻이 아니다. [호스트 루프](../../../SDK/iiGUI/src/Platform/HostIOS.mm),
   [기본 예산](../../../SDK/iiSDKCore/src/Runtime/Execution.h),
   [콜백 실행](../../../SDK/iiSDKCore/src/Runtime/EventLoop.cpp).

6. **측정 빌드의 최적화 수준 확인.** 현재 로컬 Xcode 앱의 Debug 설정은
   최적화 수준 0이며 조사에 사용한 Mac 헤드리스 시험은 Release 구성이다.
   기기에 설치된 앱의 실행 파일은 로컬 빌드와 다르고 그 구성은 확인하지 못했다. 같은 코드와
   기기에서 최적화된 계측 빌드와 Debug 빌드를 식별해 비교한 후 구조적 병목의
   크기를 판단한다.

## 다음 실기기 기록

현재 iPad 앱의 실행 파일 UUID와 빌드 구성을 확인하고, 문서 크기·확대율·
레이어 수·붓 크기·간격·불투명도를 기록한다. 브러시, 색상, 도구 전환을
각각 별도 구간으로 실행한다. 첫 자국, 이동 중, 획 확정과 Undo/Redo를 나누고
입력→화면 제출의 P50/P95/P99, 늦은 프레임과 최장 멈춤, 할당량·손상 타일 수,
CPU 및 GPU 시간을 조사한다. 실제 펜 접촉부터 화면의 빛이 바뀌기까지의
지연이나 Procreate·Photoshop·Fresco와의 동조건 비교는 이번에 측정하지 않았다.

## 후속 개선과 호스트 검증

브러시가 변경한 64×64 타일의 입력 표본은 원래의 순서를 유지한 채 타일별
벡터의 크기를 미리 확보한다. 여러 타일 준비 단계는 변경 전 픽셀을 불변
공유하되, 미리보기와 확정에 필요한 쓰기 버퍼는 분리한다. 레이어 합성은
결과가 동등한 경우에 한해 소유한 밑 레이어 버퍼를 재사용한다. Metal 표시는
이전 GPU 명령이 완료된 같은 크기의 텍스처만 재사용하며 새 픽셀은 전체
업로드한다. 완료되지 않은 텍스처에는 쓰지 않는다.

동일한 Mac 헤드리스 시험의 한 차례 전후 비교에서 128px 붓의 이동 처리 중
일반 C++ 할당 요청량은 2,586,668바이트에서 1,870,416바이트로, 512×512
표시 영역 합성은 6,292,504바이트에서 4,195,352바이트로 줄었다. 이는 각
구간의 요청 바이트 합이며 최대 메모리나 iPad 처리 시간이 아니다. 원본은
[기존 기록](../build/performance-20261110/stroke-benchmark-repeat.log)과
[수정 후 기록](../build/performance-20261110/stroke-benchmark-optimized.log)이다.

입력 순서, 필압, 타일 경계, 혼합·지우개, 선택, 긴 획, 저장 실패 복구와
Undo/Redo에 대한 회귀 시험 및 Metal 텍스처 사용 중 재사용 방지 시험을
수행했다. 실제 기기의 표시 지연과는 별도다. 이동 입력의 브러시 계산과
획 확정의 내구성 저장은 여전히 주 스레드에서 수행된다. 이 두 경로를 안전하게
작업자로 분리하는 일은 완료되지 않았다.

## iPad 후속 기록

iPad Pro 12.9형 4세대에 최적화 계측 빌드(UUID
`C3956A70-CA09-3797-87A8-49EC5E059F33`)를 설치했다. 사용자는 실제로 짧은
획과 긴 곡선을 그렸고, 지연이 줄었으나 남아 있다고 보고했다. 첫 그리기
시험에서는 암전이 없었다. 132.33초의 Time Profiler 전체 기록에는 해당 앱의
주 스레드 유효 스택 표본이 20,346개 있다. 시작과 대기 등도 포함하므로 이를
순수 드로잉 구간이나 펜에서 화면까지의 지연으로 해석할 수 없다.

실행 파일의 주소와 심볼을 대조한 추정에서는 말단 표본 중 레이어 영역 렌더링이
18.65%, 위젯 `flow_visible`이 14.14%, `logical_visible`이 10.50%, 래스터
합성이 8.00%였다. Instruments는 이미지 주소 범위가 겹친다는 경고를 냈으므로
주소 기반의 심볼 추정에는 오차가 있을 수 있다. 기록 전체에 동일 앱 프로세스의
297ms, 380ms, 695ms, 754ms 멈춤이 관찰됐지만 각 멈춤이 펜 입력 중인지
정확히 식별할 수는 없다. 기록 원본은
[iPad 추적](../build/performance-20261110/ipad-optimized.trace)과
[멈춤 표](../build/performance-20261110/ipad-optimized-hangs.xml)이다.

이에 따라 iiGUI는 기존 보유 그림의 픽셀만 바뀔 때 상호작용 관찰자를 다시
순회하지 않도록 했다. 그림이 처음 생겨 입력 클립이 달라지거나 배치·포커스·
모달 등이 변경되는 경우에는 기존 알림을 유지한다. 회귀 검사에서 관찰자
128명의 다시 계산으로 생긴 추가 할당은 동기화당 1,024바이트에서 0바이트로
줄었고, 내장 콘텐츠의 상위 위젯에도 같은 조건을 검사했다.

추가 확인 중 `CONGREGATION_PAINT_PROFILE=1`을 지정한 iPad 실행은 그리기 전에
검은 화면을 보였고, 지정하지 않거나 `0`으로 지정한 실행은 정상 화면을
표시한 적이 있다. 이후 새 빌드의 계측을 지정하지 않은 첫 실행에서도 검은
화면이 나타났고 재실행에서는 정상 표시됐다. 시작 단계의 정확한 원인은
확인되지 않았으며 계측 설정만이 원인이라고 단정할 수 없다. 해당 실행은 획별 시간
로그를 남기지 못했으며, 암전 중 추가 Instruments 기록도 기기 연결이 끊겨
1.38초에 그쳤다. 앱 실행 여부와 화면 검증은 별개이며 이 계측 경로가 iPad에서
안정적이라고 볼 수 없다.

위젯 갱신을 추가로 개선한 다음 빌드(UUID
`638B6F6D-EBC7-3B99-ACFE-BA5938650C62`)도 iPad에 설치했고 일반 실행의
초기 캔버스가 표시됐다. 151초의 대기 상태 기록에서는 250ms 이상 멈춤이
